# Using the integrated forecasting pipeline

## Notebook first

Open `notebook/Models benchmark/Models_benchmark.ipynb` and run its cells in order. It exposes data validation, causal features, future labels, purged chronological splits, train-only scaling, model architecture, training curves, ARIMA/baselines, metric tables, prediction plots, cost-aware backtesting, and artifact round trips. The default is a three-epoch CPU demonstration, not a new exhaustive benchmark. The historical multi-seed benchmark reports were not regenerated by this integration; use a fresh run when comparing the current implementation. The previous notebook is preserved in `Models_benchmark_legacy.ipynb`.

Use `LSTMModel.from_config(input_size, config)` or `GRUModel.from_config(input_size, config)` for configured return/direction/multitask forecasting, then `fit(train_x, train_y, validation_x, validation_y)`. The benchmark runner, forecasting CLI, routine training script, and bundle loader now use these public classes. Their configured mode shares `NeuralForecaster` and `RecurrentNetwork`; it does not duplicate their training loop. Default constructors and their original `train`/`predict` behavior remain explicit compatibility paths for legacy price models. Legacy pickle artifacts are not migrated into return artifacts.

## Routine training

From the repository root:

```powershell
.venv/Scripts/python.exe -m scripts.train_model --config configs/training.json --symbols BIAT --refit-production
```

Omit `--refit-production` to retain a development-fitted candidate. Change `family`, `task`, `horizon` and training budget in configuration. `--symbols BIAT ATB` runs multiple symbols with that same configuration. The default symbol is the one in the configuration; this is not an implicit all-stock sweep.

Routine training does not run the full multi-seed research grid. It trains a configured candidate with early stopping and compares validation MSE (return/multitask) or Brier score (direction) with the corresponding training-only mean/frequency baseline. Multitask promotion currently gates the return objective; probability metrics are reported separately. This baseline gate is not a claim of statistical superiority or profitability.

A rejected candidate is retained for inspection but does not replace the active model. A complete model bundle contains weights, scaler, feature order, configuration, dataset identity, and split cutoffs, with checksums. Reports are in `reports/training/`; `run.json` records per-symbol outcomes. No email is sent. Unchanged normalized data, effective configuration and implementation skip retraining when the prior bundle still verifies. `--force` deliberately reruns.

With production refit, freeze the best epoch budget selected on development validation, then fit a fresh model and scaler on all available matured labels. This explicitly retires the historical holdout: the refitted artifact must never be evaluated as unseen on that old period. Metadata records the actual label cutoff and this policy. Selection metrics describe the development candidate, not an independently evaluated production refit. Future realized forecasts are needed to evaluate the refitted model.

`artifacts/models/active.json` maps symbol/family/task/horizon to an exact immutable bundle and records prior versions. Roll back locally using `stock_forecasting.registry.rollback(root, identity)`. Treat this local registry as single-writer; the training workflow serializes runs per branch. This is not a distributed registry transaction service.

An explicit Azure backend is available with `--backend azure --data <dataset-uri> --compute <compute> --approve-cloud-action`. It submits the same script rather than claiming that runner training occurs on Azure ML. This path has not been live-tested. The Azure job performs production refit for accepted candidates. Cloud actions were not executed during implementation.

## Automation and serving

`train.yml` now tests forecasting code, pulls the checked-out DVC revision, runs candidate training on a GitHub CPU runner, restores/saves local model state with an Actions cache, and uploads bundles, reports and raw input data. Cache eviction causes retraining; it is not the durable deployment registry. `etl.yml` passes its exact committed data revision to the reusable training workflow after successful ETL. ETL itself remains manually initiated. The environment `azure-approved` is declared; required-reviewer settings must be verified in GitHub.

The existing backend mounts the shared service at `/forecast`: `/forecast/health`, `/forecast/ready`, `/forecast/v1/models`, and `/forecast/v1/predict`. Standalone service routes remain unchanged. Unversioned requests prefer the promoted model when an active manifest exists; an identity without promotion is rejected. Explicit versions remain available for research inspection. The legacy stock service also exposes `get_return_prediction`; `FORECAST_SERVING_MODE=bundles` opts its prediction function into the new response contract. Legacy `/stock` and the frontend have not been silently converted to a return-prediction contract. Agent clients initialize only when an agent request actually needs them.

`forecast-release.yml` is a separate manual release workflow. Given a reviewed training run ID, it downloads artifacts, validates promoted bundles and real inference, packages only selected models/data, builds the root Dockerfile's `packaged` target, checks readiness, publishes an image, and updates an existing forecasting App Service. It requires `FORECAST_IMAGE_REPOSITORY`, Docker Hub credentials, Azure credentials/resource group, `AZURE_FORECAST_APP_NAME`, and `FORECAST_API_KEY`. Hosting uses `FORECAST_ENV=production`. It does not create a new App Service. The original `cd.yml` remains the legacy frontend/backend release path.

Reusable workflow syntax was checked against [GitHub's workflow syntax reference](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax). YAML parsing is not proof of a successful GitHub run.
